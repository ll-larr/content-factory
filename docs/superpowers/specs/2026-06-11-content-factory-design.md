## 1. Цель

Контент-завод полного цикла: ИИ-конвейер, который проходит путь от брифа («хочу мульт-сериал про космос») до готового видео со звуком. Поддерживаемые типы контента: фильм, сериал, мультфильм, мульт-сериал, шортс (9:16). Первая версия отлаживается на **мульт-сериале**.

Расширение исходного ТЗ по итогам брейншторма: конвейер не заканчивается на видеоотрезках — добавлены **звук** (диалоги персонажей, закадровый диктор, фоновая музыка, звуковые эффекты) и **автоматическая финальная сборка** (ffmpeg).

## 2. Ключевые решения

| Вопрос | Решение |
|---|---|
| Граница цикла | Полный цикл: видеоотрезки + звук + сборка в финальное видео |
| Аудитория | Сначала личный инструмент; архитектура переносима в продукт (Agent SDK) |
| Контроль | Чекпоинты после текстовых этапов (сюжет, сценарий, персонажи) + смета в кредитах перед каждым батчем генерации |
| Платформа | Claude Code — оркестратор; Higgsfield CLI — батч-генерация; Higgsfield MCP — одиночные пробы в диалоге |
| Первый контент | Мульт-сериал, серии 3–5 мин; пилот — мини-серия 60–90 сек |
| Язык контента | Английский (диалоги, озвучка); промпты — английский |
| Картинки (база) | nano banana 2 (кадры), nano banana pro (персонажи, текст, 4K) |
| Видео (база) | Kling 2.0 (budget-режим), Seedance 2.0 (high quality) |
| Модели (поддержка) | Видео: все Kling, все Google Veo, Grok. Картинки: все Higgsfield Soul, все Seedream, Grok |
| Звук | ElevenLabs: TTS (уникальный голос на персонажа + диктор), Music, Sound Effects |

## 3. Архитектура

**Разделение ролей:**

- **Claude (режиссёр)** — всё творческое и контроль качества: исследование темы, идея, сюжет, сценарии, библия персонажей, промпты, ревью сгенерированных кадров и отрезков (vision), дайджесты для чекпоинтов.
- **Python-скрипты (рабочие руки)** — всё массовое и механическое: батч-генерация через Higgsfield CLI, поллинг, скачивание, нумерация, раскладка по папкам, TTS, сведение звука, сборка ffmpeg. В контекст Claude попадают только сводки («48/50 готово, 2 брак»).
- **Манифест проекта** — единственный источник правды о состоянии генераций; обеспечивает идемпотентный перезапуск после сбоев и продолжение работы в новой сессии.

**Почему так (а не всё через MCP в диалоге):** серия мульт-сериала = ~100–150 генераций; прогон каждой через контекст диалога упирается в потолок контекста и хрупок к сбоям. Скрипты с манифестом решают обе проблемы. Отдельное приложение (Agent SDK) отложено: главная неизвестность проекта — качество конвейера, оно выясняется дешёвыми итерациями в Claude Code; скиллы и скрипты затем переносятся в приложение без переписывания.

## 4. Структура контент-проекта

```
projects/<имя>/
├── project.json           # бриф (см. ниже)
├── manifest.json          # состояние всех генераций (см. §10)
├── research.md            # выжимка исследования темы
├── bible/
│   ├── idea.md            # главная идея, общая стилистика      [артефакт 1 ТЗ]
│   ├── season-arc.md      # сквозной сюжет на все серии
│   ├── style-guide.md     # канонический блок визуального стиля
│   └── characters/        # библия персонажей                   [артефакт 2 ТЗ]
│       ├── <имя>.md       # характер, роль, канонический блок внешности,
│       │                  # голос ElevenLabs, промпты
│       └── <имя>-ref.png  # утверждённый референс (character sheet)
└── episodes/
    └── ep01/
        ├── script.md      # сценарий серии, разбитый на 5-сек биты [артефакт 3 ТЗ]
        ├── shots.json     # машиночитаемый план съёмки (см. §8)
        ├── storyboard/    # 001.png, 002.png, ...                [артефакт 4 ТЗ]
        ├── segments/      # 001.mp4 (кадры 1→2), 002.mp4 (2→3)…  [артефакт 5 ТЗ]
        ├── audio/
        │   ├── dialogue/  # реплики по битам
        │   ├── narration/ # закадровый текст
        │   ├── music/     # фоновая музыка
        │   └── sfx/       # звуковые эффекты
        └── ep01_final.mp4 # готовая серия со звуком              [новый артефакт]
```

**`project.json`** — параметры брифа из ТЗ: тип контента, тематика, длительность, число и длительность серий, возрастная аудитория (для мультконтента), комментарии-пожелания, для шортсов — баннер и его позиция (верх/низ); плюс: модель картинок, модель видео, режим качества (high quality = отрезки 5 с / budget = 10 с), `review_strictness` (low/medium/high, по умолчанию medium), язык.

**Нумерация** — по ТЗ: кадры и отрезки получают порядковые номера в имени файла; end-кадр отрезка N = start-кадр отрезка N+1 (отрезок 001 = кадры 001→002, отрезок 002 = кадры 002→003, …).

Отличия от исходного ТЗ (намеренные): персонажи вынесены в отдельный этап **до** раскадровки (в ТЗ — п. 5.1 внутри раскадровки), потому что кадры генерируются с референсами персонажей и внешность дешевле утвердить до попадания героя в 60 кадров. Этапы 8–9 добавлены.

**Протокол чекпоинта.** Каждый чекпоинт начинается с дайджеста — пользователь не обязан читать полные файлы:

- чекпоинт «сюжет»: краткое содержание на 7–10 предложений + логлайн каждой серии в одну строку;
- чекпоинт «сценарий»: поэпизодный пересказ серии + ключевые диалоги;
- чекпоинт «персонажи»: карточка на каждого — имя, роль, характер одной строкой + референс-картинка + аудиопроба голоса.

В каждом дайджесте: что изменилось после правок пользователя и открытые вопросы. Полные файлы — по ссылкам для углубления.

Этапы 6–9 идут без чекпоинтов, но перед каждым батчем — **смета в кредитах с подтверждением пользователя**.

## 6. Модельный парк и карточки моделей

Скиллы этапов модель-агностичны: внутри скилла — процесс, best practices конкретной нейросети — в `knowledge/<семейство>/<модель>.md`. Скилл подтягивает карточку по выбору модели в project.json.

**Карточка модели** (по `_template.md`):

1. **Матрица возможностей:** поддержка start/end кадра, нативный звук, макс. длительность клипа, разрешения/форматы, ценовой уровень (кредиты), особые режимы.
2. **Best practices промптинга:** структура промпта, сильные/слабые стороны, типовые ошибки, примеры.

`generate_batch.py` читает матрицу возможностей и **валидирует выбор до траты кредитов**: схема склейки требует start/end кадра — если модель этого не умеет, завод предупреждает и предлагает совместимую. (Kling — умеет, подтверждено; по конкретным версиям Veo/Grok — проверить при наполнении карточек.)

**Скоуп наполнения на запуск:** полные карточки для базовых моделей (nano banana 2, nano banana pro, Kling 2.0, Seedance 2.0); карточки остальных заявленных семейств (Kling все, Veo все, Grok, Soul все, Seedream все) — каркас с матрицей возможностей, best practices наполняются по мере использования.

## 7. Консистентность персонажей

Три уровня защиты:

1. **Канонический блок описания** — в карточке персонажа фиксированный текст внешности (англ.), который вставляется в каждый промпт **дословно**, без пересказов.
2. **Референс-изображения** — на этапе 5 nano banana pro генерирует character sheet (несколько ракурсов), пользователь утверждает; референс передаётся как input-изображение в каждую генерацию кадра с персонажем.
3. **Style guide** — канонический блок общей стилистики в каждом промпте без исключения.

Уникальные имена персонажей — по ТЗ (сквозная адресация между нейросетями). Опция: Soul Characters (тренировка персонажа в Higgsfield, ≈40 кредитов) — проверить на пилоте, нужна ли для мультперсонажей или достаточно референсов.

## 8. Механика генерации (этапы 6–7)

1. **План съёмки.** Claude по утверждённому сценарию строит `shots.json`: для каждого кадра — номер, промпт, ссылки на референсы; для каждого отрезка — пара кадров (N → N+1) и промпт движения. Это единственный источник правды для скриптов.
2. **Смета.** `generate_batch.py` считает стоимость батча в кредитах до запуска (команда расчёта стоимости Higgsfield CLI); запуск — только после подтверждения пользователя.
3. **Батч.** Отправка задач пачками → поллинг → скачивание → нумерация → раскладка по папкам → запись в манифест.
4. **Ревью.** Claude просматривает результаты (vision): соответствие промпту, референсам, стайл-гайду — по рубрике §9. Брак → перегенерация (лимит 3 попытки на единицу, дальше вопрос пользователю).

## 9. Рубрика ревью (порог брака)

**Критичный брак → перегенерация:**
- персонаж не соответствует референсу (лицо, телосложение, одежда);
- анатомические артефакты (лишние пальцы, искажённые лица);
- кадр не выполняет задачу сценария (не то действие, нет ключевого объекта);
- сломан стиль (например, фотореализм вместо мультяшности);
- кадр непригоден для склейки (end-кадр не состыкуется со следующим отрезком).

**Некритичные расхождения → принять:**
- оттенки фона, второстепенные детали окружения;
- мелкие отличия позы/ракурса, не меняющие смысл кадра.

**Главное правило:** деталь критична, только если явно прописана в сценарии или библии. Не оговорено — любой вариант годится. Каждый реджект в манифесте ссылается на конкретное нарушенное правило.

Механизмы: `review_strictness` в project.json (low/medium/high); кадры с некритичными замечаниями помечаются `accepted_with_notes` — пользователь может пробежать список и точечно перегенерить.

**Управление строгостью:** меняется в любой момент, в том числе посреди генерации, — (а) фразой в диалоге («поставь строгость high») или (б) слэш-командой `/strictness <low|medium|high>` (кастомная команда Claude Code). Новая строгость применяется к последующим ревью; принятые кадры не пересматриваются без явной просьбы. В будущем продукте — переключатель в UI, меняющий то же поле project.json.

## 13. Обработка ошибок

- **Брак контента** — рубрика §9, лимит 3 перегенерации, далее вопрос пользователю.
- **Стыки отрезков** — совпадение end N = start N+1 гарантировано схемой; Claude дополнительно проверяет плавность движения на стыках.
- **Технические сбои** (сеть, очередь Higgsfield) — ретраи с экспоненциальной паузой; статус задач восстанавливается из манифеста.
- **Исчерпание кредитов** — остановка с внятным сообщением; точка возобновления — манифест.
