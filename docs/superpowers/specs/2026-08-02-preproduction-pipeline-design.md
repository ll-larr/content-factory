# Пре-продакшн конвейера: от брифа до shots.json — дизайн-документ

**Дата:** 2026-08-02
**Статус:** утверждён по итогам брейншторма
**Базовая спека:** `2026-06-11-content-factory-design.md` (этапы 1–6, §5–§9)

---

## 1. Цель и граница

Закрыть первую половину конвейера — сейчас её нет вообще. Вторая половина (генерация
кадров и отрезков, ревью, сведение звука, сборка) работает и доказана живыми
генерациями; путь «бриф → `shots.json`» делается руками, из-за чего конвейер не
сходится встык.

**Вход:** заполненный `projects/<name>/project.json`.
**Выход:** `projects/<name>/episodes/<ep>/shots.json`, проходящий гейты `generate_batch.py`.

Скоуп — этапы 1–5 базовой спеки плюс написание `shots.json` (в базовой спеке это
начало этапа 6). Остановиться на этапе 5 нельзя: разрыв «сценарий → shots.json»
остался бы ручным и конвейер всё равно не проверить концом-в-конец.

## 2. Ключевые решения

| Вопрос | Решение |
|---|---|
| Гейты первой половины | Жёсткие, как во второй: код читает состояние и отказывается работать (exit 3) |
| Где живёт состояние одобрения | Frontmatter самого артефакта + хеш содержимого + хеши зависимостей |
| Разделение труда | Python — механика (состояние, гейты, валидация); скиллы — творчество |
| Поверхность | CLI `scripts/factory.py` + скиллы `.claude/skills/factory*` |
| Управление | Общая команда `/factory` (автономный режим) + команда на каждый этап |
| Режимы автономности | Три: остановка на чекпоинтах (дефолт), авто-одобрение текста, полная |
| Этап 2 (research) | Необязательный (флагом/командой), гейта нет, но делает НАСТОЯЩИЙ веб-поиск |
| Голоса персонажей | Поле в карточке есть, аудиопроба не генерится (Фаза 4 отложена) |
| Референсы персонажей | Обычная платная генерация через существующий манифест и `review.py` |


Всё, кроме `bible/`, `research.md`, `script.md` и `shots.json`, уже поддержано кодом.

## 4. Контракт frontmatter

Каждый текстовый артефакт первой половины начинается с блока:

```yaml
---
kind: idea | season-arc | style-guide | character | script | research
status: draft | approved
approved_at: 2026-08-02T14:30:00Z        # только при status: approved
content_sha: 8f14e45fceea167a5a36de...   # sha256 тела ПОСЛЕ frontmatter, на момент одобрения
depends_on:                               # чем этот артефакт был обусловлен
  - {path: bible/idea.md, sha: 3c59dc048e...}
  - {path: bible/season-arc.md, sha: b6d767d2f8...}
---
```

**Зачем `content_sha`.** Текстовый артефакт — не кадр: его правят руками, и это
нормальная работа. Без отпечатка «жёсткий гейт» проверял бы только галочку и
пропускал изменённый после одобрения текст, то есть был бы декоративным.

**Зачем `depends_on`.** Ловит вторую беду: артефакт сам не менялся, но его основание
уехало (переписал `idea.md` через неделю после одобрения сценария).

`content_sha` считается по телу документа после закрывающего `---`, чтобы простановка
`approved_at` не меняла хеш сама по себе.

**Сценарий дополнительно объявляет состав серии:**

```yaml
kind: script
characters: [Мурзик, Барсик]
```

Состав объявляется явно, а не выводится поиском имени по тексту. Поиск подстрокой врёт
в обе стороны: «Мурзик смотрит на фотографию Барсика» записал бы Барсика в участники
сцены, а персонажа, названного иначе, не нашёл бы вовсе. Тот же ход принят в §10 для
промптов кадров. Сценарий без поля `characters` — пустой состав: серия без персонажей
технически возможна (заставка, титры).

Без этого поля гейт дырявый, и это проверено: персонаж, впервые появившийся во второй
серии, проходил насквозь — карточки первой серии одобрены, значит «всё готово», и кадры
второй уходили в платную генерацию без описания и референса нового героя.

**Что во что входит `depends_on`** — фиксированная карта по `kind`, а не свободный
список, иначе два запуска `approve` дадут разный результат:

| `kind` | `depends_on` |
|---|---|
| `research` | — |
| `idea` | — (опирается на `project.json`, он не артефакт) |
| `season-arc` | `bible/idea.md` |
| `style-guide` | `bible/idea.md` |
| `character` | `bible/idea.md`, `bible/style-guide.md`, все `episodes/*/script.md`, объявившие персонажа в своём `characters` |
| `script` | `bible/idea.md`, `bible/season-arc.md` |

## 5. Машина состояний и гейты

Модуль `scripts/factory/preprod.py`:

```python
artifact_state(path) -> "missing" | "broken" | "draft" | "approved" | "stale_self" | "stale_deps"
stage_gate(project, stage, episode=None) -> list[str]     # пусто = можно
next_stage(project) -> tuple[str, str | None]             # (stage, episode)
```

- `broken` — файл есть, но не читается (битый frontmatter). Отдельное состояние ради
  формулировки: сказать про такой файл «не одобрен (draft)» значит послать человека
  одобрять то, что не разбирается.
- `stale_self` — `status: approved`, но текущий хеш тела ≠ `content_sha`.
- `stale_deps` — свой хеш сходится, но хеш какого-то файла из `depends_on` не сходится.

Оба состояния гейт трактует как «не одобрено», с разной формулировкой проблемы:
человеку надо понимать, перечитывать ему свой файл или чужой.

**Цепочка гейтов:**

| Этап | Требует |
|---|---|
| 2 research | ничего (необязательный) |
| 3 story (idea, season-arc, style-guide) | валидный `project.json` |
| 4 script (эпизод) | idea + season-arc `approved` |
| 5 characters | script эпизода `approved`; каждый персонаж из его `characters` имеет одобренную карточку |
| 6 shots.json | script `approved`, style-guide `approved`, каждый персонаж из `characters` этой серии имеет одобренную карточку, все референсы приняты ревью |

Нарушение — код возврата 3, тот же, что у `generate_batch`/`mix_audio`/`assemble`,
чтобы поведение было одинаковым по всему конвейеру.

## 6. Поверхность команд

**CLI `scripts/factory.py`** — детерминированная механика, полностью покрывается тестами:

```bash
python scripts/factory.py init    --project projects/pilot
python scripts/factory.py status  --project projects/pilot
python scripts/factory.py next    --project projects/pilot
python scripts/factory.py check   --project projects/pilot --stage script --episode ep01
python scripts/factory.py approve --project projects/pilot bible/idea.md
```

- `init` — скаффолд дерева по `project.json` (пустые артефакты со `status: draft`).
- `status` — таблица «артефакт → состояние», источник правды для новой сессии.
- `next` — первый незакрытый шаг; на нём стоит драйвер автономного режима.
- `check` — гейт этапа, exit 0 или 3.
- `approve` — **единственное место, где появляется `status: approved`**; проставляет
  `approved_at`, считает `content_sha` и заполняет `depends_on` по фактическим хешам.

Скилл не имеет права проставить `approved` сам: одобрение — действие человека, и след
о нём должен остаться в файле, а не в диалоге.

**Скиллы `.claude/skills/`:** `factory-research`, `factory-story`, `factory-script`,
`factory-characters`, `factory-storyboard` — по этапу; `factory` — драйвер автономного
режима. Вызываются как `/factory-script`, `/factory`.

**Устройство скилла этапа** (одинаково у всех пяти, отличается творческая середина):

1. Спросить `factory.py check`; гейт закрыт — остановиться и объяснить, чем именно.
2. Прочитать ровно те артефакты, от которых этап зависит (не весь проект), и
   `bible/craft-notes.md` — свод правил по ремеслу этого проекта (§11).
3. Сделать свою работу.
4. Записать выход со `status: draft`.
5. Чекпоинтный этап — показать дайджест (§8) и остановиться.

## 7. Режимы автономности

В `project.json`:

```json
{ "autonomy": "checkpoints", "budget_usd": 25 }
```

| Режим | Поведение на чекпоинте | Гейт трат |
|---|---|---|
| `checkpoints` (дефолт) | Останавливается, показывает дайджест, ждёт `approve` | спрашивает |
| `auto_approve` | Сам вызывает `approve`, идёт дальше | спрашивает |
| `full` | Сам вызывает `approve`, идёт дальше | не спрашивает, но не превышает `budget_usd` |

`budget_usd` обязателен при `autonomy: full`; смета сверх остатка бюджета
останавливает прогон, а не урезает батч. Потраченное считается из манифеста
(`credits_total()`).

При `auto_approve` и `full` в `approved_at` артефакта пишется пометка, что одобрение
автоматическое — иначе по файлу не отличить решение человека от решения машины.

**Сколько эпизодов за прогон.** Все, по порядку `ep01 → ep02 → …` до числа из
`project.json.episodes`. `season-arc` пишется один раз на весь сезон, дальше сценарий
и раскадровка идут поэпизодно; закончив эпизод, драйвер берёт следующий, а не
останавливается. В режиме `checkpoints` это означает остановку на каждом чекпоинте
каждого эпизода — то есть первый прогон дойдёт до чекпоинта сценария `ep01` и будет
ждать. В `full` — до последнего эпизода или до исчерпания `budget_usd`, что раньше.

## 8. Этапы

| # | Этап | Выход | Чекпоинт | Дайджест |
|---|---|---|---|---|
| 2 | research | `research.md` | нет | — (веб-поиск; включается флагом) |
| 3 | story | `idea.md`, `season-arc.md`, `style-guide.md` | ✋ | пересказ 7–10 предложений + логлайн каждой серии строкой |
| 4 | script | `episodes/<ep>/script.md` | ✋ | поэпизодный пересказ + ключевые диалоги |
| 5 | characters | `bible/characters/*.md` + `*-ref.png` | ✋ | карточка на каждого: имя, роль, характер строкой + референс |
| 6 | storyboard | `episodes/<ep>/shots.json` (плейсхолдеры, §10) | нет (дальше гейт трат) | — |

Дайджесты — по протоколу базовой спеки §5. В каждом: что изменилось после правок
пользователя и открытые вопросы.

`style-guide.md` вынесен в этап 3 (в базовой спеке он не был привязан к этапу):
канонический блок стиля нужен раньше персонажей, потому что референс персонажа
генерируется уже в этом стиле.

## 9. Персонажи — единственные деньги первой половины

Отдельного механизма нет. Референс-лист персонажа — обычная платная генерация
картинки, поэтому идёт через существующее: новая стадия `generate_batch.py --stage
characters`, item в манифесте (`kind: character_ref`), ревью через `review.py`
(accept / accept-notes / reject / requeue, лимит `max_rejections`).

Модель берётся из `project.json` как и для кадров; по базовой спеке §6 для character
sheet уместна `nano_banana_2` (читаемый текст, несколько ракурсов).

Это закрывает три уровня консистентности из базовой спеки §7 без нового кода:
канонический блок внешности — в карточке персонажа, референс — в манифесте и в `refs`
кадров, стайл-гайд — в каждом промпте.

## 10. shots.json и машинные проверки консистентности

`factory-storyboard` пишет `shots.json` в существующем формате (`factory/shots.py`,
инварианты `load_shots` не меняются).

### Плейсхолдеры вместо копий канонических блоков

Базовая спека §7 требует вставлять канонический блок стиля и канонический блок
внешности персонажа в каждый промпт **дословно, без пересказов**. Буквальное
исполнение — копировать оба блока в текст каждого из ~60 кадров серии. Это плохо по
двум причинам: тысячи токенов дублированного текста, который Claude пишет и потом
перечитывает, и шанс незаметно перефразировать блок при копировании, то есть сломать
ровно ту консистентность, ради которой правило существует.

Поэтому `shots.json` хранит **плейсхолдеры**, а разворачивает их код перед отправкой:

```json
{"n": 12, "prompt": "{{style}} {{char:murzik}} presses a red button, same camera angle"}
```

`generate_batch.build_jobs` подставляет тексты из `bible/style-guide.md` и
`bible/characters/<name>.md` и отправляет провайдеру полную строку. Развёрнутый промпт
пишется в манифест — иначе по файлам не восстановить, что реально ушло провайдеру.

Ссылка на карточку в самом промпте невозможна: промпт уходит по HTTP во внешнюю
модель, у неё нет ни репозитория, ни файловой системы. Дословность нужна не нам, а
генератору. Плейсхолдер решает это тем, что дословность обеспечивает код на выходе,
а не человек на входе.

Побочные выгоды: правка карточки персонажа применяется ко всем кадрам сразу, без
переписывания шестидесяти промптов; перефразировать блок физически невозможно.

### Проверки гейта

1. В промпте каждого кадра есть `{{style}}`.
2. Каждый `{{char:<name>}}` ссылается на существующую карточку персонажа со
   `status: approved`.
3. `refs` кадра содержит принятый ревью референс каждого персонажа, объявленного
   через `{{char:...}}`.
4. В промпте не осталось неизвестных плейсхолдеров `{{...}}`.

Плейсхолдер — ещё и явное объявление «этот персонаж в кадре», поэтому определять
присутствие эвристикой по имени не нужно: «Мурзик смотрит на фотографию Барсика»
объявляет только Мурзика, и референс Барсика не требуется.

### Разметка канонических блоков в источниках

Блоки размечаются в артефактах явными маркерами, чтобы их можно было извлечь машинно:

```markdown
<!-- canonical:style -->
flat 2D cartoon, thick outlines, saturated palette, ...
<!-- /canonical:style -->
```

Отсутствие маркеров в `style-guide.md` или в карточке персонажа — проблема гейта
этапа 3/5, а не этапа 6: разворачивать будет нечего.

## 11. Обратная связь по творческим артефактам

Код проверяется тестами, текст — нет. Единственный судья того, хорош ли сценарий,
живой ли характер и держится ли сюжет — человек. При этом молчание двусмысленно:
пользователь мог одобрить, а мог просто не дойти. **Трактовать молчание как похвалу
нельзя** — иначе завод закрепит неудачные приёмы и будет повторять их из серии в серию.

**Механика.**

1. Скилл коммитит артефакт в git сразу после записи, до правок человека. Это даёт
   бесплатный диф «что написала машина» против «что стало после человека» — без
   отдельного хранилища снимков.
2. Frontmatter получает поле `feedback`:
   - `none` — правок не было и оценки не было. Это **«неизвестно»**, а не «хорошо».
   - `pending` — человек изменил файл, причина правок не разобрана.
   - `recorded` — оценка зафиксирована в `bible/craft-notes.md`.
3. `factory.py status` показывает эту колонку наравне с состоянием одобрения.
4. `factory.py diff --project P <artifact>` — что человек изменил с момента генерации.

**Команда `/factory-feedback`** (отдельная, потому что на неё не должен полагаться
основной поток — она вызывается, когда у человека есть время):

- находит артефакты в `pending` и `none`;
- по каждому `pending` показывает диф, **формулирует свою догадку о причине правки** и
  просит подтвердить или поправить — так молчаливая правка превращается в урок;
- по каждому `none` спрашивает оценку 1–5 и комментарий; пропуск оставляет `none`,
  а не превращает в «хорошо»;
- дописывает вывод в `bible/craft-notes.md`.

**`bible/craft-notes.md` — свод правил, а не журнал.** В файл пишется вывод из
комментария пользователя, а не сам комментарий. Комментарий и диф — вход; выход —
правило в повелительном наклонении с однострочной причиной и коротким указанием
происхождения:

```markdown
## Диалоги
- Не давать персонажу проговаривать то, что зритель уже видит в кадре —
  реплика дублирует картинку и тормозит сцену. (ep01/script, 2026-08-02)

## Сюжет
## Персонажи
## Визуальные описания
```

Почему так, а не журналом обсуждений: стадия читает этот файл перед каждой работой, и
ей нужна инструкция, а не история переписки. Журнал пришлось бы каждый раз заново
интерпретировать — то есть выводить правило по новой, каждый раз возможно иначе.
Вывод делается один раз, при записи.

Группировка по областям — чтобы правила находились и **сливались**: близкое правило не
дублируется, а уточняет существующее. Это же тормозит разрастание файла: правил
конечное число, реплик — нет.

**Правило выводит `/factory-feedback` и обязательно показывает пользователю до
записи.** Неверно выведенное правило хуже отсутствующего: оно молча применится ко всем
следующим сериям. Пользователь подтверждает формулировку или правит её — это дешевле,
чем потом искать, откуда взялась систематическая ошибка.

Оценка 1–5 в правило не превращается и в файл не пишется — она нужна для тренда по
сериям. Если оценки сценариев не растут, значит правила не работают, и чинить надо

## 14. Открытые вопросы

1. `craft-notes.md` (§11) хранит правила, а не реплики, и близкие правила сливаются —
   поэтому растёт медленно. Но потолок всё равно есть: когда файл перестанет влезать в
   контекст стадии, разделять по областям и грузить только релевантную. Пока не
   оптимизировать.
2. Разворачивание плейсхолдеров (§10) увеличивает промпт на стороне провайдера. У
   моделей есть предел длины промпта, и на длинных карточках персонажей его можно
   пробить. Замерить на первой боевой серии; при необходимости — ограничивать длину
   канонических блоков на этапе 3/5, а не резать их при разворачивании.

**Закрыто решением пользователя 2026-08-02:** автономный режим обрабатывает ВСЕ
эпизоды по порядку, а не один (§7); `research` делает настоящий веб-поиск, а не
опирается на знания модели (§8); определение «персонаж в кадре» снято переходом на
плейсхолдеры (§10) — эвристика по имени больше не нужна.
