# Пре-продакшн конвейера: от брифа до shots.json — дизайн-документ

**Дата:** 2026-08-02
**Статус:** утверждён по итогам брейншторма
**Базовая спека:** `2026-06-11-content-factory-design.md` (этапы 1–6, §5–§9)

---

## 1. Цель и граница

Закрыть первую половину конвейера — сейчас её нет вообще. Вторая половина (генерация
кадров и отрезков, ревью, сведение звука, сборка) работает и доказана живыми
генерациями; путь «бриф → `shots.json`» делается руками, из-за чего конвейер не
сходится встык.

**Вход:** заполненный `projects/<name>/project.json`.
**Выход:** `projects/<name>/episodes/<ep>/shots.json`, проходящий гейты `generate_batch.py`.

Скоуп — этапы 1–5 базовой спеки плюс написание `shots.json` (в базовой спеке это
начало этапа 6). Остановиться на этапе 5 нельзя: разрыв «сценарий → shots.json»
остался бы ручным и конвейер всё равно не проверить концом-в-конец.

## 2. Ключевые решения

| Вопрос | Решение |
|---|---|
| Гейты первой половины | Жёсткие, как во второй: код читает состояние и отказывается работать (exit 3) |
| Где живёт состояние одобрения | Frontmatter самого артефакта + хеш содержимого + хеши зависимостей |
| Разделение труда | Python — механика (состояние, гейты, валидация); скиллы — творчество |
| Поверхность | CLI `scripts/factory.py` + скиллы `.claude/skills/factory*` |
| Управление | Общая команда `/factory` (автономный режим) + команда на каждый этап |
| Режимы автономности | Три: остановка на чекпоинтах (дефолт), авто-одобрение текста, полная |
| Этап 2 (research) | Необязательный, включается флагом/командой, гейта на него нет |
| Голоса персонажей | Поле в карточке есть, аудиопроба не генерится (Фаза 4 отложена) |
| Референсы персонажей | Обычная платная генерация через существующий манифест и `review.py` |

## 3. Дерево артефактов

```
projects/<name>/
├── project.json              бриф, модели, режим автономности, бюджет
├── manifest.json             генерации: кадры, отрезки, референсы персонажей
├── research.md               опционально (этап 2)
├── bible/
│   ├── idea.md               идея + общая стилистика          [этап 3]
│   ├── season-arc.md         сквозной сюжет на все серии      [этап 3]
│   ├── style-guide.md        канонический блок визуального стиля [этап 3]
│   └── characters/
│       ├── <name>.md         характер, роль, канонический блок внешности, голос [этап 5]
│       └── <name>-ref.png    утверждённый референс (character sheet)
└── episodes/<ep>/
    ├── script.md             сценарий, разбитый на биты       [этап 4]
    ├── shots.json            план съёмки                      [этап 6]
    ├── storyboard/           существует (вторая половина)
    ├── segments/             существует
    ├── audio/                существует
    └── final/                существует
```

Всё, кроме `bible/`, `research.md`, `script.md` и `shots.json`, уже поддержано кодом.

## 4. Контракт frontmatter

Каждый текстовый артефакт первой половины начинается с блока:

```yaml
---
kind: idea | season-arc | style-guide | character | script | research
status: draft | approved
approved_at: 2026-08-02T14:30:00Z        # только при status: approved
content_sha: 8f14e45fceea167a5a36de...   # sha256 тела ПОСЛЕ frontmatter, на момент одобрения
depends_on:                               # чем этот артефакт был обусловлен
  - {path: bible/idea.md, sha: 3c59dc048e...}
  - {path: bible/season-arc.md, sha: b6d767d2f8...}
---
```

**Зачем `content_sha`.** Текстовый артефакт — не кадр: его правят руками, и это
нормальная работа. Без отпечатка «жёсткий гейт» проверял бы только галочку и
пропускал изменённый после одобрения текст, то есть был бы декоративным.

**Зачем `depends_on`.** Ловит вторую беду: артефакт сам не менялся, но его основание
уехало (переписал `idea.md` через неделю после одобрения сценария).

`content_sha` считается по телу документа после закрывающего `---`, чтобы простановка
`approved_at` не меняла хеш сама по себе.

**Что во что входит `depends_on`** — фиксированная карта по `kind`, а не свободный
список, иначе два запуска `approve` дадут разный результат:

| `kind` | `depends_on` |
|---|---|
| `research` | — |
| `idea` | — (опирается на `project.json`, он не артефакт) |
| `season-arc` | `bible/idea.md` |
| `style-guide` | `bible/idea.md` |
| `character` | `bible/idea.md`, `bible/style-guide.md`, все `episodes/*/script.md`, где персонаж упомянут |
| `script` | `bible/idea.md`, `bible/season-arc.md` |

## 5. Машина состояний и гейты

Модуль `scripts/factory/preprod.py`:

```python
artifact_state(path) -> "missing" | "draft" | "approved" | "stale_self" | "stale_deps"
stage_gate(project, stage, episode=None) -> list[str]     # пусто = можно
next_stage(project) -> tuple[str, str | None]             # (stage, episode)
```

- `stale_self` — `status: approved`, но текущий хеш тела ≠ `content_sha`.
- `stale_deps` — свой хеш сходится, но хеш какого-то файла из `depends_on` не сходится.

Оба состояния гейт трактует как «не одобрено», с разной формулировкой проблемы:
человеку надо понимать, перечитывать ему свой файл или чужой.

**Цепочка гейтов:**

| Этап | Требует |
|---|---|
| 2 research | ничего (необязательный) |
| 3 story (idea, season-arc, style-guide) | валидный `project.json` |
| 4 script (эпизод) | idea + season-arc `approved` |
| 5 characters | script эпизода `approved` |
| 6 shots.json | script `approved`, style-guide `approved`, все карточки персонажей `approved`, все референсы приняты ревью |

Нарушение — код возврата 3, тот же, что у `generate_batch`/`mix_audio`/`assemble`,
чтобы поведение было одинаковым по всему конвейеру.

## 6. Поверхность команд

**CLI `scripts/factory.py`** — детерминированная механика, полностью покрывается тестами:

```bash
python scripts/factory.py init    --project projects/pilot
python scripts/factory.py status  --project projects/pilot
python scripts/factory.py next    --project projects/pilot
python scripts/factory.py check   --project projects/pilot --stage script --episode ep01
python scripts/factory.py approve --project projects/pilot bible/idea.md
```

- `init` — скаффолд дерева по `project.json` (пустые артефакты со `status: draft`).
- `status` — таблица «артефакт → состояние», источник правды для новой сессии.
- `next` — первый незакрытый шаг; на нём стоит драйвер автономного режима.
- `check` — гейт этапа, exit 0 или 3.
- `approve` — **единственное место, где появляется `status: approved`**; проставляет
  `approved_at`, считает `content_sha` и заполняет `depends_on` по фактическим хешам.

Скилл не имеет права проставить `approved` сам: одобрение — действие человека, и след
о нём должен остаться в файле, а не в диалоге.

**Скиллы `.claude/skills/`:** `factory-research`, `factory-story`, `factory-script`,
`factory-characters`, `factory-storyboard` — по этапу; `factory` — драйвер автономного
режима. Вызываются как `/factory-script`, `/factory`.

**Устройство скилла этапа** (одинаково у всех пяти, отличается творческая середина):

1. Спросить `factory.py check`; гейт закрыт — остановиться и объяснить, чем именно.
2. Прочитать ровно те артефакты, от которых этап зависит (не весь проект).
3. Сделать свою работу.
4. Записать выход со `status: draft`.
5. Чекпоинтный этап — показать дайджест (§8) и остановиться.

## 7. Режимы автономности

В `project.json`:

```json
{ "autonomy": "checkpoints", "budget_usd": 25 }
```

| Режим | Поведение на чекпоинте | Гейт трат |
|---|---|---|
| `checkpoints` (дефолт) | Останавливается, показывает дайджест, ждёт `approve` | спрашивает |
| `auto_approve` | Сам вызывает `approve`, идёт дальше | спрашивает |
| `full` | Сам вызывает `approve`, идёт дальше | не спрашивает, но не превышает `budget_usd` |

`budget_usd` обязателен при `autonomy: full`; смета сверх остатка бюджета
останавливает прогон, а не урезает батч. Потраченное считается из манифеста
(`credits_total()`).

При `auto_approve` и `full` в `approved_at` артефакта пишется пометка, что одобрение
автоматическое — иначе по файлу не отличить решение человека от решения машины.

## 8. Этапы

| # | Этап | Выход | Чекпоинт | Дайджест |
|---|---|---|---|---|
| 2 | research | `research.md` | нет | — |
| 3 | story | `idea.md`, `season-arc.md`, `style-guide.md` | ✋ | пересказ 7–10 предложений + логлайн каждой серии строкой |
| 4 | script | `episodes/<ep>/script.md` | ✋ | поэпизодный пересказ + ключевые диалоги |
| 5 | characters | `bible/characters/*.md` + `*-ref.png` | ✋ | карточка на каждого: имя, роль, характер строкой + референс |
| 6 | storyboard | `episodes/<ep>/shots.json` | нет (дальше гейт трат) | — |

Дайджесты — по протоколу базовой спеки §5. В каждом: что изменилось после правок
пользователя и открытые вопросы.

`style-guide.md` вынесен в этап 3 (в базовой спеке он не был привязан к этапу):
канонический блок стиля нужен раньше персонажей, потому что референс персонажа
генерируется уже в этом стиле.

## 9. Персонажи — единственные деньги первой половины

Отдельного механизма нет. Референс-лист персонажа — обычная платная генерация
картинки, поэтому идёт через существующее: новая стадия `generate_batch.py --stage
characters`, item в манифесте (`kind: character_ref`), ревью через `review.py`
(accept / accept-notes / reject / requeue, лимит `max_rejections`).

Модель берётся из `project.json` как и для кадров; по базовой спеке §6 для character
sheet уместна `nano_banana_2` (читаемый текст, несколько ракурсов).

Это закрывает три уровня консистентности из базовой спеки §7 без нового кода:
канонический блок внешности — в карточке персонажа, референс — в манифесте и в `refs`
кадров, стайл-гайд — в каждом промпте.

## 10. shots.json и машинные проверки консистентности

`factory-storyboard` пишет `shots.json` в существующем формате (`factory/shots.py`,
инварианты `load_shots` не меняются).

Гейт добавляет три проверки, которых раньше не было:

1. В промпте каждого кадра **дословно** присутствует канонический блок стайл-гайда.
2. Если в кадре есть персонаж — **дословно** присутствует его канонический блок внешности.
3. `refs` кадра ссылается на принятый ревью референс этого персонажа.

Базовая спека §7 требует вставлять эти блоки дословно, без пересказов. Раз дословно —
проверяется подстрокой. Это единственное место, где консистентность персонажей
перестаёт быть пожеланием в промпте и становится проверкой.

Канонические блоки размечаются в исходных артефактах явными маркерами, чтобы их можно
было извлечь машинно:

```markdown
<!-- canonical:style -->
flat 2D cartoon, thick outlines, saturated palette, ...
<!-- /canonical:style -->
```

Присутствие персонажа в кадре определяется по имени из `bible/characters/` в тексте
промпта. Имена персонажей по базовой спеке §7 уникальны, поэтому совпадение
однозначно.

## 11. Тестирование

Скиллы юнит-тестами не покрываются и не должны: весь риск в резолвере и гейтах, а они
чистый Python без сети. Фикстура собирает поддельное дерево проекта в `tmp_path`.

Покрыть: порядок гейтов по цепочке §5; `stale_self`; `stale_deps`; что `approve`
пишет корректные `content_sha`/`depends_on`; что простановка `approved_at` не ломает
`content_sha`; три проверки `shots.json` из §10; порядок шагов `next_stage` в каждом
из трёх режимов автономности; поведение при `budget_usd` на исходе.

## 12. Вне скоупа

- Генерация звука (Фаза 4) — отложена, начинается с отдельного brainstorming.
- Аудиопробы голосов на чекпоинте персонажей — поле в карточке есть, генерации нет.
- Шортс-баннер и 9:16 в сборке — отложены ранее, здесь не трогаются.
- Многосерийность за пределами последовательной обработки эпизодов: `season-arc`
  пишется на все серии сразу, но сценарии и раскадровки идут по одному эпизоду.

## 13. Открытые вопросы

1. Сколько эпизодов обрабатывает автономный режим за один прогон — один или все по
   порядку? Предполагается один; пересмотреть после первого пилота.
2. Нужен ли `research` веб-поиск или достаточно знаний модели — решается на первом
   проекте, где тема требует фактуры (научпоп).
3. Порог «персонаж присутствует в кадре» по совпадению имени может дать ложное
   срабатывание на упоминании в третьем лице. Если всплывёт на пилоте — размечать
   персонажей кадра явным полем в `shots.json`.
