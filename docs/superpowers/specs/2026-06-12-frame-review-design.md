# Ревью кадров: отклонение и перегенерация — дизайн

**Дата:** 2026-06-12
**Статус:** утверждён пользователем (brainstorming 2026-06-12, повторное одобрение в новой сессии)
**Контекст:** основная спека `2026-06-11-content-factory-design.md` (§8 шаг 4, §9, §10, §13);
находка №2 смоука фазы 1 — `done` ставится сразу после скачивания и терминален,
отклонить готовый кадр штатно невозможно, окна ревью в жизненном цикле нет.

---

## 1. Проблема

Оркестратор `generate_batch.py` завершает успешную генерацию статусом `done`,
который терминален. Этап ревью (спека §8 шаг 4, §9) не имеет места в машине
статусов: принять/отклонить сгенерированный кадр нельзя без ручной правки
manifest.json. Чекпоинт «segments только после приёмки кадров» не существует.

## 2. Решения пользователя (зафиксированы, не пересматривать)

1. Ревью делает Claude-режиссёр после каждого батча + пользователь выборочно.
2. Жёсткий чекпоинт: стадия segments ЗАБЛОКИРОВАНА, пока кадры, на которые
   ссылаются отрезки, не приняты ревью.
3. Перегенерация: ревьюер правит промпт в shots.json (единственный источник
   промптов); `reject_reason` в манифесте — журнал причин, не источник промпта.
4. Лимит: **2 отклонения** на единицу → стоп, решение человека.

## 3. Машина статусов (`scripts/factory/manifest.py`)

Новый статус `generated` = «сгенерировано и скачано, ждёт ревью».
`done` меняет смысл: теперь это «принято ревью», по-прежнему терминален.

Разрешённые переходы (полная замена таблицы `ALLOWED`):

| Из | В | Смысл |
|---|---|---|
| `pending` | `generating` | взято в работу |
| `generating` | `generated` | успешная генерация (файл скачан) |
| `generating` | `pending` | технический сбой → возврат в очередь |
| `generated` | `done` | ревью: принято |
| `generated` | `accepted_with_notes` | ревью: принято с замечаниями |
| `generated` | `rejected` | ревью: отклонено |
| `rejected` | `pending` | перегенерация |
| `accepted_with_notes` | `pending` | точечная перегенерация по желанию |
| `done` | — | терминален |

Прямые переходы `generating → done/rejected/accepted_with_notes` УДАЛЯЮТСЯ:
единственный путь к приёмке — через `generated` (ревью).

Новое поле item: `reject_count` (int, по умолчанию 0, добавляется в
`KNOWN_FIELDS` и в дефолты `add()`). `set_status` инкрементирует его
**автоматически** при каждом переходе в `rejected` — инвариант живёт в одном
месте, вызывающие не обязаны помнить про счётчик.

Правило «`rejected` требует `reject_reason`» сохраняется как есть.

Докстринг модуля обновить под новую машину.

## 4. Оркестратор (`scripts/generate_batch.py`)

1. **Успешная генерация завершается в `generated`** (вместо `done`),
   с теми же полями `file`, `job_id`, `credits_spent`.
2. **Автоперевод rejected → pending перед батчем:** после `manifest.add(...)`
   и восстановления зависших `generating`, все items текущего батча в статусе
   `rejected` с `reject_count < max_rejections` переводятся в `pending` —
   перегенерация по актуальному shots.json (jobs строятся из shots.json на
   каждом запуске, исправленный промпт подхватывается сам). Items с
   `reject_count >= max_rejections` НЕ переводятся и пропускаются с громким
   сообщением (id + причина последнего реджекта + «требуется решение
   человека»). `accepted_with_notes` автоматически НЕ перегенерируется —
   переход в `pending` для них только по явной команде (см. §5 `requeue`).
3. **Чекпоинт segments:** при `--stage segments`, до сметы и любых трат,
   проверить кадры, на которые ссылаются `start_frame`/`end_frame` отрезков:
   каждый соответствующий item (`{ep}/storyboard/{n:03d}`) должен существовать
   в манифесте и иметь статус `done` или `accepted_with_notes`. Иначе —
   напечатать список проблемных кадров (id + текущий статус или «не
   генерировался») и выйти с **exit code 3**. Код 2 остаётся за валидацией
   модели, 0/1 — как сейчас.
4. **Сообщение idle-прогона:** если `todo` пуст, но есть items батча в статусе
   `generated` — вместо «Всё уже сгенерировано» сообщить «N единиц ждут ревью»
   (со списком id). Полностью принятый батч отвечает как раньше.
5. Механика общая для кадров и отрезков: отрезки тоже завершаются в
   `generated` и проходят ревью тем же CLI; гейт «сборка только после приёмки
   отрезков» — фаза 2, здесь не делаем.

## 5. CLI ревью (`scripts/review.py`) — новый скрипт

Интерфейс для ревьюера — человека и Claude-режиссёра. Запуск из корня репо.
Общий аргумент `--project <путь>` (манифест один на проект, id содержат
эпизод). Подкоманды:

- `list [--status <s>]` — таблица items: id, status, attempts, reject_count,
  file. Фильтр по статусу опционален (типовой вызов: `--status generated`).
- `accept <id> [<id> ...]` — `generated → done` для каждого id.
- `accept-notes <id> --notes "..."` — `generated → accepted_with_notes`,
  notes сохраняются в поле `notes`.
- `reject <id> --reason "..."` — `generated → rejected`, причина в
  `reject_reason` (журнал), счётчик инкрементируется манифестом.
- `requeue <id>` — `rejected → pending` либо `accepted_with_notes → pending`.
  Это механизм «решения человека» после лимита: команда работает независимо
  от `reject_count` (счётчик НЕ сбрасывается — журнал честный; следующий
  реджект снова остановит автоперегенерацию).

Ошибки (`ManifestError`: неизвестный id, недопустимый переход) — внятное
сообщение в stderr, exit code 1, манифест не повреждён (atomic save уже есть).
Все изменения — через `Manifest.set_status` + `save()`, никакой своей логики
переходов. UTF-8 reconfigure для Windows-консоли — как в generate_batch.py.

## 6. `project.json`: `max_rejections`

Новое опциональное поле брифа: `max_rejections` — целое ≥ 0, дефолт **2**.
`factory/project.py`: поле в dataclass `Project`, валидация типа/диапазона в
`load_project` (не-int или отрицательное → `ProjectError`).

## 7. Совместимость

Старые манифесты валидны без миграции: `done` остаётся легальным терминальным
статусом, items без `reject_count` читаются как есть (счётчик появится при
первом `add()` нового item; для существующих items отсутствие ключа
допустимо — читать через `.get("reject_count", 0)` там, где он нужен).

## 8. Тесты

- `tests/test_manifest.py`: новые переходы разрешены, удалённые
  (`generating → done` и т.п.) запрещены; `reject_count` инкрементируется
  автоматически и только при переходе в `rejected`; `done` терминален.
- `tests/test_generate_batch.py`: успешный путь завершается в `generated`;
  автоперевод `rejected → pending` при `reject_count < max`; пропуск с
  сообщением при достижении лимита; гейт segments → exit 3 (кадр не принят /
  кадр отсутствует в манифесте); принятые кадры (`done` и
  `accepted_with_notes`) гейт пропускают; idle-сообщение про «ждут ревью».
- Новый `tests/test_review.py`: каждая подкоманда (list/accept/accept-notes/
  reject/requeue), reject без --reason → ошибка, недопустимый переход →
  exit 1, requeue работает при `reject_count >= max`.
- `tests/test_project.py`: дефолт и валидация `max_rejections`.
- Существующие тесты, предполагающие `generating → done`, обновить.

## 9. Отвергнутые альтернативы

- **Разрешить `done → rejected`** — рушит семантику `done` как надёжного
  сигнала для жёсткого чекпоинта segments.
- **Отдельное поле `reviewed` рядом со status** — два измерения состояния,
  комбинаторика переходов, YAGNI.
