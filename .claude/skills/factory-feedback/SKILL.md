# Разбор обратной связи

Отдельный от основного потока скилл (спека §11) — запускается, когда у
человека есть время посмотреть, что он в итоге поправил, а не сразу после
каждого чекпоинта. Работает только с текстовыми frontmatter-артефактами,
которые перечисляет `factory.py status`: `bible/idea.md`,
`bible/season-arc.md`, `bible/style-guide.md`, `bible/characters/*.md`,
`episodes/*/script.md`, `research.md`.

**`episodes/<ep>/shots.json` сюда не входит.** Это простой JSON без
YAML-frontmatter; `factory.py status` его вообще не перечисляет
(`_project_artifacts` в `scripts/factory.py` не заглядывает в `episodes/*`
дальше `script.md`), а `factory.py feedback`/`approve` на нём упадут
(`load_artifact` требует шапку, которой в чистом JSON нет).

## Что делаешь

1. ```bash
   python scripts/factory.py status --project <проект>
   ```
   Колонки: артефакт, состояние (`missing|broken|draft|approved|stale_self|
   stale_deps`), `feedback` (`none|pending|recorded`). Возьми строки с
   `feedback: pending` и `feedback: none`.

2. По каждому `pending` (человек изменил файл после того, как его записал
   скилл этапа, причина ещё не разобрана):
   ```bash
   python scripts/factory.py diff --project <проект> <артефакт>
   ```
   Диф — против последнего git-коммита файла (скилл этапа коммитит сразу
   после записи, это и есть база сравнения). Если коммита нет вовсе,
   `diff` честно скажет «нет базовой версии в git — сравнивать не с чем» —
   тогда пропусти этот артефакт, разбирать нечего.

   Сформулируй СВОЮ догадку о причине правки — что было не так по-твоему и
   что человек этим правил — и покажи её пользователю ДО того, как что-то
   запишешь. Получив подтверждение или поправку, выведи из этого правило (см.
   ниже).

3. По каждому `none` (ни правок, ни оценки — это **«неизвестно», не
   «хорошо»**) спроси оценку 1–5 и комментарий. Пропуск — оставь `none` как
   есть, не переводи молчание в правило и не меняй `feedback` без реального
   ответа.

## Как писать в craft-notes

`bible/craft-notes.md` — свод правил, а не журнал обсуждений. Файл не
скаффолдится `factory.py init` — если его ещё нет, создай сам, этим же шагом.

Правило — не реплика пользователя, а вывод из неё: повелительное наклонение +
однострочная причина + короткое происхождение `(файл, дата)`, под одну из
фиксированных групп:

```markdown
## Сюжет

## Диалоги
- Не давать персонажу проговаривать то, что зритель уже видит в кадре —
  реплика дублирует картинку и тормозит сцену. (ep01/script, 2026-08-02)

## Персонажи

## Визуальные описания
```

Перед добавлением проверь, нет ли уже близкого правила в той же группе — если
есть, уточни существующую строку вместо дубликата: правил конечное число,
реплик — нет, и группировка нужна именно для того, чтобы файл не разрастался
без предела.

**Покажи сформулированное правило пользователю ДО записи в файл.** Неверно
выведенное правило хуже отсутствующего — оно молча применится ко всем
следующим сериям, и оспорить задним числом будет сложнее, чем один раз
подтвердить формулировку сейчас.

Оценка 1–5 в `craft-notes.md` НЕ пишется — она нужна только для тренда по
сериям, не для правил (спека §11: «если оценки сценариев не растут, значит
правила не работают, и чинить надо саму петлю»). Ни код, ни спека не
определяют, где именно хранить сам числовой тренд — эта часть вне скоупа
данного скилла и текущей реализации; просто спроси оценку и обсуди её с
человеком в рамках этого разговора, не пытайся сам придумать для неё
хранилище.

## После записи правила

```bash
python scripts/factory.py feedback --project <проект> <артефакт> --state recorded
```
`--state` принимает только `none|pending|recorded` (`FEEDBACK_STATES` в
`scripts/factory/preprod.py`) — опечатка в значении вернёт код 1 со списком
допустимых значений.

Закоммить `bible/craft-notes.md` в git по завершении шага, как и любой другой
текстовый артефакт — если человек потом поправит уже записанное правило,
`factory.py diff` при следующем прогоне это тоже покажет:
```bash
git add <проект>/bible/craft-notes.md
git commit -m "feat(preprod): craft-notes <проект>"
```
